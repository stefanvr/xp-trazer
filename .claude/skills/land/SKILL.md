# Land

**Owns.** What happens at the moment a goal lands: the point where the owner approves a merge to
main. Right now that is one task — clearing `doc/scratchpad/` — and this is where further landing
tasks go as they earn their place.

**Not here.** The git mechanics around it. Branch before a goal, commit task-sized, push before
returning, approval before merging, delete the branch after — all in
[CLAUDE.md](../../CLAUDE.md), which is also where the hook that calls this skill lives.

**Run it before the merge, not after.** Clearing the scratchpad is a change to the goal's own branch,
so it belongs in the goal's history. A goal that lands with its working notes still in the tree has
not finished landing.

---

## The rule

**Nothing is deleted that cannot be either regenerated or found in a document that owns it.**

That single test is what licenses the deletion, and it is why the work below happens before the
`rm` rather than instead of it.

## Every open item has exactly three fates

Read `doc/scratchpad/` end to end and give each item one:

1. **Fix it.** The change is an edit to a document. Make it now, on this branch, before the merge.
2. **Decide it.** The thing is deliberate. Record *that* in the document that owns it — the routing
   table in [CLAUDE.md](../../CLAUDE.md) names which — so it stops being an inconsistency at all. If
   the decision is temporary, it is an override, and `doc/guide-override.md` wants what would end it.
3. **Leave it.** Do nothing, and let it be found again. **Legitimate only for derived content**, and
   that restriction is the whole of the rule above.

Then delete the files.

## Derived and original notes are not the same

- **Derived** — a `todo-discovery` snapshot, or anything else regenerated by re-running a routine.
  Deleting it costs nothing: the inconsistency is still in the documents, so the next run finds it
  again. **Delete without ceremony**, including its unresolved entries.
- **Original** — an observation, a sketch, a measurement, a "careful, X breaks Y". Nothing
  regenerates it, so deleting it is a real loss. It must be promoted to the document that owns it, or
  it must be genuinely scratch. If you cannot name the document it belongs to and it is not scratch,
  that is the signal to ask rather than to delete.

## No permanent todo list

A backlog file is the obvious fourth fate and it is the wrong one:

- It is a **cache of something computable**, and it goes stale in the direction nobody sees — a fixed
  item stays listed, and reads as authority.
- It forces the discovery routine to **suppress findings that are still true in the documents**, on
  the authority of a hand-maintained file. That is a second source of truth competing with `doc/`.
- It is a document that **owns no decision**, which is the one thing every document in `doc/` must do.

A finding either gets fixed, or gets decided and recorded, or comes back next run. A list is a fourth
state that looks like progress and is not.

## Scope

`doc/scratchpad/` only, and the `.gitkeep` stays so the directory survives being empty.

**`doc/brainstorm/` is not cleared.** A brainstorm records how a specification got its content and is
superseded by that specification rather than deleted — the `brainstorm` skill carries that rule.

## When not to run it

- **When the merge is not a landing** — merging main into a branch, or a branch that was not a goal.
- **Mid-goal, to tidy up.** The notes are for the goal in progress; clearing them early throws away
  the working state of something unfinished.
