# Collaboration guidelines

**Owns.** Who decides what, how the two sides exchange it, and where a lesson goes once it is learned.

**Not here.** The principles that settle a technical question, and how the code is shaped. The order
work happens in, and the mechanics of doing it, are the workflow's.

**Written to outlive the project.** Lift it onto a different one unchanged.

---

## Starting

- **Ask what the goal of the session is** — not what to do next, but what would make this session
  finished.

## Deciding

- **Don't decide on the owner's behalf — not the product, not the scope.** Options and a
  recommendation, then wait. Confirm before it is recorded, not after.

## Reporting

- Structure it — a table wherever the content has repeating fields.
- Mark a question as a question. Never leave an ask implied inside an observation, and say plainly
  when a note needs no answer.

## Where a lesson goes

- **A repeatable way of working becomes a routine that can be invoked**, wired into the workflow —
  never prose inside a document that owns decisions. A document owns a decision; a routine is a
  procedure, and the two go stale differently.
- **A rule that governs the project belongs in the tree.** An agent's private memory is not
  committed, not reviewable in a diff, not visible in the working copy, and reaches no other person
  and no other agent. **The test: would this rule still need to hold if a different person or a
  different agent did the next goal?** If yes it belongs in the repository, and memory is at most a
  private copy of it.
- **Say where a lesson went.** *"I saved that"* invites exactly the wrong inference. Name the file,
  and say plainly when something is still only in private memory and therefore binds nobody.
